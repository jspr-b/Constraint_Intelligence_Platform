# fest-parallel

Runs one festival sequence at a time with parallel agents. You are the **coordinator**: you plan the
split, start the workers, merge their branches, run the tests and gates, and own all fest and PLUR
writes. Workers only write code on their own branch.

Keep it simple. If a sequence does not split cleanly, run it as one agent. A wrong split costs more
than it saves.

## 0. Before you start

- Festival dirs live in `~/festivals/active/<name>-<ID>/`. The repo is `~/Constraint_Intelligence_Platform`.
- Paradev project id: run `superset projects list --local` (CIP is `38f75802-ffb0-4cff-84e5-501315962db1`).
- The festival branch (e.g. `wizard/ci0005`) is the base for every worker. Its working tree must be
  clean and pushed: `git status --porcelain` empty, `git push`. Workers fork from the pushed branch.
- `.superset/` setup gives each workspace its own `.env`, ports and Docker project `cip-<name>`.

## 1. Plan the split (stop for approval)

1. `cd` to the festival, read `SEQUENCE_GOAL.md` and every task in the sequence. Use `fest deps` to see
   which tasks depend on each other.
2. Only the **build tasks** run in parallel. Walkthrough, testing, review, iterate and fest_commit
   tasks are gates: the coordinator runs them after the merge.
3. For each build task, write down the files it will touch (read the code; use gitnexus if indexed).
4. Group tasks that can run together. Rules:
   - **At most 3 workers** per group.
   - **No two workers touch the same file.** If they would, run them one after the other.
   - **Hot files belong to one worker, or to a contract step that runs first:** Alembic migrations
     (one migration number per group), `packages/schema`, `apps/api/openapi.json`,
     `apps/web/src/lib/api/schema.d.ts`, `pyproject.toml`, `package.json`, lockfiles, `CLAUDE.md`, ADRs.
   - If tasks share an API shape (backend + frontend), first do a **contract step** alone: the
     endpoint shape, shared types and migration, committed to the festival branch. Then fork workers.
   - Generated files (`openapi.json`, `schema.d.ts`) are regenerated by the coordinator after merge,
     never by workers.
5. Show the user a short table: group, task, worker branch, files owned. **Wait for approval.**

## 2. Start the workers

For each task in the group:

```bash
superset ws create --local --project <project-id> \
  --name <id>-<seq>-<task> --branch <festival-branch>--<seq>-<task> \
  --base-branch <festival-branch> --tag <ID> \
  --agent claude --prompt "<worker prompt>"
```

Worker prompt (fill in the brackets, keep the rest):

```
You are a worker on festival <ID>, task <absolute path to task file>.
Read that task file, its SEQUENCE_GOAL.md and FESTIVAL_RULES.md, and the CLAUDE.md sections it names.
Work ONLY in this workspace folder (not ~/Constraint_Intelligence_Platform) on branch <worker-branch>.
You own only these files: <list>. Do not edit any other file. If you must, stop and report why.
Do not touch: migrations other than <number or none>, generated files, lockfiles, CLAUDE.md, ADRs.
Your stack runs on the ports in this folder's .env (./.superset/run.sh); never use the main cip database.
Build with tests (error cases first). Run the tests for what you changed.
Commit on your branch with message "[<ID>] <task>: <what>" and push it.
Do NOT run fest commands (no fest task completed, no fest commit). Do NOT call plur_learn.
When done, or blocked, end with a report:
DONE|BLOCKED, files changed, tests run and result, anything you learned that should be remembered,
and any change you think the contract or another task needs.
```

Then monitor: `superset snapshot`, `superset terminals read`, `superset sessions read`. Answer a
blocked worker with `superset sessions send`. Do not let a worker widen its own file list.

## 3. Merge (stop for approval)

When all workers in the group report DONE:

1. Show the user one line per branch: files changed, tests, open issues. **Wait for approval.**
2. On the festival branch, merge the worker branches one at a time (`git merge --no-ff <branch>`).
   Conflict → stop and show it; do not guess a resolution.
3. Regenerate generated files if the API changed, then run the full checks
   (`pnpm -r lint typecheck test`, `uv run pytest`, `bash scripts/check-generated.sh`).
   A failure → find which branch caused it and stop.
4. Push the festival branch.

## 4. Gates and bookkeeping (coordinator only)

1. Mark the build tasks done: `fest task completed <task>` (in the festival dir).
2. Run the sequence's walkthrough, testing, review and iterate tasks yourself, as in a normal run;
   the walkthrough needs freshly built images and a real browser check.
3. Commit with `fest commit --stage=false` after staging only your own paths.
4. PLUR: save only what is merged and true. Uncertain notes from workers go in with
   `commitment: draft`. Run `plur_tensions` after each group and fix contradictions.

## 5. Clean up

Archive each worker workspace (`superset ws archive <id> --local`); teardown removes its Docker
project. Delete merged worker branches locally and on origin.

Then go to the next group or sequence. Try a new kind of split on a small sequence first.
